### Addendum — the HTML-wrapping "infrastructure finding" above had an actual fix

Keith asked whether there was a way around the `/stream/` endpoint's HTML wrapping, rather than living with the hand-unwrap workaround. There was: `archive.org/download/{id}/{id}_djvu.txt` (not `/stream/`) returns the file as `Content-Type: text/plain` directly — confirmed against all three identifiers touched this run (Hooper, Nowell, Ridley), following the redirect with `curl -L`. `/stream/` is the human-facing viewer page (hence the HTML), while `/download/` is the direct file-serving route and was the right tool all along.

Updated `CLAUDE.md` and `AGENTS.md` (three matching spots each — the controlled-vocabulary source-type table, the Stage 2 archive_ocr download command, and the "Notes on Sources" Archive.org entry) to use `/download/` and recorded why, so this doesn't need rediscovering. Also corrected `source_url` on the `hooper-pestilence-homily`, `nowell-catechism`, and `ridley-bocardo-letters` queue entries to the `/download/` form — Hooper's is already imported so this is just accurate metadata, but Nowell's and Ridley's future runs can now `curl` straight into `clean-archive-ocr.mjs`'s expected plain-text input with no unwrapping step at all. Dale's `dale-the-atonement` is unaffected by this fix — that identifier 404s on every archive.org route, `/download/` included, so the blocker there is genuinely a wrong identifier, not the endpoint.
